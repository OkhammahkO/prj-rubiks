# TM1638 Display & Buzzer

8-digit 7-segment LED display with 8 physical buttons and (on most modules) 8 individual
LEDs, plus a separate RTTTL piezo buzzer. Hardware tested; pins confirmed working.

## Hardware

| Function | Pin |
|---|---|
| TM1638 STB | GPIO 14 |
| TM1638 CLK | GPIO 41 |
| TM1638 DIO | GPIO 42 |
| Buzzer (RTTTL, LEDC ch 6) | GPIO 44 |

GPIO42 briefly looked dead during assembly — turned out to be a stray wire in the
harness shorting DIO to ground, not a damaged pin. See `docs/robot.md` "Hardware"
for the full diagnosis (a raw GPIO toggle test that bypasses the TM1638 driver
entirely). GPIO47 is a confirmed-working spare if DIO ever needs to move again.

The 8 LEDs are exposed as diagnostic switches (`TM1638 LED 1`-`8`) and driven two ways:
each button's own LED flashes momentarily on that button's press (see "Physical
buttons" below), and the whole bar runs one of six status routines tied to
`solver_status` (see "LED routines" below). The 8 buttons are exposed as diagnostic
binary sensors (`TM1638 Button 1`-`8`). Every button beeps and flashes its own LED on
press; buttons 1-4 also trigger a real action, 5-8 are still placeholder feedback only.

## Current implementation

**Display** (`display: platform: tm1638` in `rubiks-solver.yaml`): shows the
`solver_status` text sensor, right-padded to 8 characters, refreshed every 500ms.
Possible values: `IDLE`, `SCAN N`, `FACE N`, `HOMING`, `SCAN END`, `SOLVING`, `DONE`,
`CHK ARM`. While status is exactly `SOLVING`, the display instead shows `MV NNN` —
the live `Moves Remaining` sensor — counting down as the solve executes.

**Moves Remaining** (`moves_remaining_sensor:` on the `rubiks_solver` component):
counts down from the full robot-action count (flips/spins/rotates — the same count
reported to HA in `execute_solution`'s `move_count` response) to 0 as
`execute_solution()` progresses, via `mark_action_boundary_()` calls placed in
`plan_flip_`/`plan_spin_`/`plan_rotate_` (`rubiks_solver.cpp`). Purely additive
bookkeeping — it observes `step_idx_` crossing precomputed boundaries and never
influences step timing or servo positions, so it can't introduce a collision risk.
Only meaningful while `SOLVING`; stale (holds the last solve's count) otherwise.

**Physical buttons** (`TM1638 Button 1`-`8`, `binary_sensor: platform: tm1638` in
`rubiks-solver.yaml`): all 8 beep and flash their own LED on press. Buttons 1-4 also
trigger a real action:

| Button | Action | Mechanism |
|---|---|---|
| 1 | Start Scan | `homeassistant.action`: `button.press` on `button.rubiks_cube_scanner_robot_start_scan` |
| 2 | Abort | `homeassistant.action`: `button.press` on `button.rubiks_cube_scanner_robot_abort` |
| 3 | Confirm Safe & Home | Local — calls `confirm_safe_and_home()` directly, same as the existing HA-side template button |
| 4 | Scramble | `homeassistant.action`: `button.press` on `button.rubiks_cube_scanner_scramble` |

Buttons 5-8 are still placeholder (beep + flash only) — the "Solve" step doesn't need
its own button since `rubiks_solve_dispatcher` (`ha_automations/rubiks_robot.yaml`)
already fires it automatically once scanning finishes; "Advance Face" stayed
HA-dashboard-only since it's a debug aid, not a normal-use action.

**Why route Start Scan/Abort/Scramble through `homeassistant.action` instead of
calling the equivalent ESPHome action (`start_scan()`/`stop()`) directly**: the HA-side
buttons do more than their firmware counterparts. `RobotStartScanButton`/
`RobotAbortButton` also clear stale scan state (`scanned_faces` etc.) before/alongside
triggering the robot — a bare `esphome.rubiks_solver_start_scan` call skips that,
risking a previous incomplete scan's leftover data bleeding into the new one.
`homeassistant.action: button.press` on the exact HA entity_id runs the identical code
path as clicking it on the dashboard, so there's one source of truth instead of two
implementations that can drift. `confirm_safe_and_home()` has no such HA-side wrapper
(no scan state involved), so a direct local call is already complete and correct.
Requires ESPHome 2025.10.0+ (`homeassistant.action` bidirectional response handling) —
this project is on 2026.7.2, so it's available.

**Also requires enabling it on the HA side, per device**: Settings → Devices &
Services → ESPHome → this device → gear/Configure icon → "Allow the device to perform
Home Assistant actions". Off by default. Without it, the ESP32 sends the action
request but HA never subscribed to receive it, so it's silently dropped — firmware
logs a warning (`Home Assistant action '...' dropped; ...`) but nothing else visibly
happens, which looks identical to a firmware/wiring bug from the button/beep/LED side
(those all still fire fine, since they don't depend on this toggle at all).

**`Test: Display Hello`** (diagnostic button) — bare hardware check, writes `"HELLO"`
directly to the status text sensor the display already mirrors, bypassing the solver's
state machine entirely (no servo motion, no beep — `"HELLO"` doesn't match any RTTTL
condition). If this doesn't show up, the problem is display wiring (GPIO 14/41/42), not
firmware logic — useful as a first check during initial assembly, independent of
whether the rest of the component is even working yet.

**Buzzer** (`rtttl:` component, driven by `on_value` on the same `solver_status` sensor):

| Status | Sound |
|---|---|
| `FACE N` | single short beep |
| `HOMING` | 2 low beeps (`g4,p,g4`) |
| `SCAN END` | 3 beeps at the original pitch (`c6,p,c6,p,c6`) |
| `DONE` | short ascending 4-note melody |

`HOMING` and `SCAN END` deliberately differ in both pitch *and* beep count, not just
pitch, so they're distinguishable on a small piezo buzzer. Both are timed to land in
genuine pauses rather than over servo motion — see
`docs/collision-prevention.md` ("Settle pads at the scan-return boundary") and the
1300ms delay at the top of `rubiks_solve_dispatcher` in `ha_automations/rubiks_robot.yaml`
for how each is kept clear of the motion around it.

**LED routines** (`script:` entries in `rubiks-solver.yaml`, triggered from the same
`status_sensor` `on_value` block as the beeps above): each status gets a visually
distinct pattern across the 8-LED bar, so the robot's state reads at a glance without
looking at the display.

| Status | Routine | Script id |
|---|---|---|
| `FACE N` | Light that face's LED and leave it on — a 1-6 progress bar builds across the scan | (inline, parses `N` from the status string) |
| `HOMING` | Reverse "collapse" — LEDs 6→1 turn off in sequence, mirroring the cube physically returning home | `homing_led_collapse` |
| `SCAN END` | One quick marquee chase across all 8, then off | `scan_end_chase` |
| `SOLVING` | Continuous back-and-forth "Cylon" sweep across all 8 | `solving_led_sweep` |
| `DONE` | Forward chase + reverse chase + a final all-on flash | `done_celebration` |
| `CHK ARM` | Slow alternating even/odd blink — deliberately not a chase, so it reads as "different, needs a human" | `chk_arm_led_blink` |
| `IDLE` | All LEDs off (safety net — an abort mid-scan/mid-solve can reach `IDLE` without passing through `HOMING`/`DONE`, whose routines clean up after themselves) | `idle_led_reset` |

`solving_led_sweep` and `chk_arm_led_blink` are the two continuous routines — each
uses a `while:` action whose condition re-checks the live `solver_status` on every
cycle, so it self-terminates (and clears its LEDs) the instant status changes, with no
external stop signal needed. All six scripts are LED-only side effects with no
servo/timing interaction, so none of them can affect step timing or introduce a
collision risk regardless of how long an animation runs.

## Pipelined (not yet implemented)

- **Scan face colour label** — show the face colour letter instead of the position
  number while paused at a face (`FACE  G` instead of `FACE 4`) — the firmware already
  knows `SCAN_FACES[scan_face_idx_]` locally, and it's arguably more recognizable to
  someone watching than the numeric position.
- **Error codes** — distinct display patterns for scan error, solve error, comms lost.
- **Rejected-command feedback** — `start_scan()`/`execute_solution()`'s guards
  (`state_ != IDLE`, `needs_confirm_before_move_`, `!believed_home_`) currently only log
  a warning; the display doesn't change at all, so a rejected button press looks
  identical to nothing happening. Worth a brief status like `NOT HOME` or `REJECT`.
- **Already-solved feedback** — an empty solution string (cube already solved) currently
  never publishes `SOLVING`/`DONE` at all, so it silently does nothing on-screen. Worth a
  brief `SOLVED` status.
- **"READY" prompt** when waiting for cube placement.
- **Solve timer** — count up during `execute_solution`, freeze at completion.
- **Routine re-home button** — `confirm_safe_and_home()` currently only matters after an
  unclean reset; there's no low-stakes "just re-home now" control for routine use (e.g.
  after manually nudging the cube holder) without that precondition.
- **Display brightness control** — `intensity:` is hardcoded to `1` in
  `rubiks-solver.yaml`; a number entity (0-7) would let brightness be tuned live for
  room lighting, mirroring the camera's `LED Brightness` on the HA side.

Deliberately **not** pipelined: a "computing solve" status shown while HA runs kociemba
between `SCAN END` and `SOLVING` — would need a new HA→ESP32 call just for that one
status update, real complexity for a minor nicety.

See `docs/features.md` for how these rank against the project's other pipelined
features overall.
